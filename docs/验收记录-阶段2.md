## 三、端到端链路

```
data/raw/*.md
  → loaders（md 优先，pdf 用 PyMuPDF 抽文本层，扫描件直接报需要 OCR）
  → clean_lines（页眉页脚/页码/网页导航/目录点线/表格分隔）
  → normalize（康熙部首 + 零宽字符 + 全角 + CJK 间隙）
  → parse_law（编→章→节→条，三重防误判）
  → build_chunks（父块=整条，子块=条内句/项切分，chunk 300 / overlap 50）
  → bge-m3（dense 1024 + sparse，CPU fp32）
  → MySQL document_chunks（1465 父 + 1470 子）/ Milvus law_chunks（1470 子向量）
```

实测耗时：三部法律合计 **9 分 42 秒**（CPU 向量化；民法典 1263 子块 455 秒）。
若换 CUDA 版 torch，预计可压到 1 分钟内。

## 五、本阶段修复的问题（都留了测试）

| 问题 | 原因 | 修复 |
|---|---|---|
| 绑定参数误伤 | SQL 里 `LIKE '%:p14'` 被 SQLAlchemy 当占位符 | 测试改用 `article_no` 过滤 |
| 增量跳过失效 | MySQL JSON 列读回是字符串，`dict(str)` 抛 ValueError | `get_document_by_sha1` 统一 `json.loads` |
| 上传 500 | 缺 `python-multipart` | 补依赖 |
| 知识库名乱码 | docker entrypoint 的 mysql 客户端非 utf8mb4，种子数据被 latin1 写入 | `02_seed_kb.sql` 首行加 `SET NAMES utf8mb4` + 回填两行 |
| 父子块"看起来少字" | 列表分页只显示前 2 条 | 核对 316 = 265 + 51，确认无丢失 |
| overlap 形同虚设 | 按字符截尾在句末边界处恒为空 | 改为"整句回带"，并加断言 |

## 六、已知限制

- **向量化在 CPU 上跑**：本机 PyPI 版 torch 2.14.1 是 `+cpu` 构建（`torch.cuda.is_available()=False`），
  配置里保留 `EMBEDDING_DEVICE`，装 CUDA 版 torch 后改回 `cuda` 即可，代码会自动检测并告警回退。
- **接口暂无鉴权**：JWT 在阶段 4 与用户体系一起接入。
- **PDF 走的是 Markdown 优先策略**：三部法律都用了 `data/raw/*.md`；PDF 加载器已实现并单测通过
  （26 页、0 空页、12,803 字），扫描件会明确报"需要 OCR"而不是入库空文本。
