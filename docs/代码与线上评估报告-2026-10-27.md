# LawAnswer 项目代码与线上评估报告

> 评估日期：2026-10-27
> 评估方式：通读全部后端 Python 源码、前端 Vue3/TS 源码、测试与部署配置；本机跑通离线测试套件（675 passed / 49 skipped，24.75s）；实测线上 https://jsq0917.xin/chat（含 /api/health、匿名 SSE 问答、响应头、端口暴露面）。
> 结论先行：**代码工程质量高、可维护性好，达到"简历级作品 + 可继续迭代"的水准；但线上正发生一次 P0 事故（Redis 磁盘持久化失败 → 验证码 502 → 全站无法登录），且存在 3 个由"本地单机假设"带进线上环境的适配缺口。**

---

## 一、总体评估

### 1.1 项目结构与架构（评分：A）

六层职责边界清晰，依赖方向单向，符合分层架构最佳实践：

```
api（路由/鉴权/限流）→ orchestration（意图+路由+缓存）→ retrieval（混合检索）
                                              ↘ generation（Prompt+SSE+落库）
ingest（解析→分块→向量化）→ db（MySQL/Milvus/Redis 客户端）
config.py（唯一配置源，pydantic-settings + 分组视图）
```

值得肯定的设计点：

| 项 | 说明 |
|---|---|
| 单一配置源 | 全部参数集中在 `config.py`，字段校验、跨字段约束、生产密钥强制（`JWT_SECRET` 非默认值）、密钥进 `.env` 即拒绝启动 |
| 依赖可注入 | settings / db / embedder / llm_client 全部支持注入，单测可离线替换 |
| 双源路由 | 高频问答（MySQL+Redis）与法条检索（Milvus）解耦，6 条路由矩阵写进代码注释，可审计 |
| 容错分层 | SSE 链路 7 层容错（意图降级/生成重试/断流保 partial/客户端断开落库/检索降级/缓存降级/无资料不编造） |
| 幂等入库 | 整篇替换 + SHA1 增量 + 就地重建，避免父子块与向量错位 |

### 1.2 代码质量（评分：A）

- 本机实测 **675 个离线测试全部通过**（24.75s），49 个 integration 测试按标记跳过（需真实依赖），覆盖鉴权/SSE/路由/检索/分块/配置/落库等主干。
- 安全实践到位：bcrypt cost=12 + 哑校验防时序枚举账号、验证码一次性消费、Redis Lua 原子限流、SQL 全参数化（动态 WHERE 子句只由白名单内部值拼装）、上传文件名净化、kb 删除目录穿越校验、密钥指纹缓存键（不明文入内存键）。
- 代码注释质量高：每个设计取舍都写了"为什么"（如交错融合 vs max 聚合、等权 RRF vs 加权、为何不用 XFF 取 IP），后续维护者可直接接上下文。
- 前端：Vue3 组合式 + Pinia + 全类型化 API 层 + `test_frontend_contract.py` 锁定前后端契约，SSE 事件归并收敛在 store，视图层很薄。

### 1.3 可维护性（评分：A-）

- 文档完备：README（一键跑通 + API 全表 + 常见问题）、REPORT.md（量化基线）、8 阶段验收记录、阿里云部署方案、简历 STAR。
- 一键脚本：`bootstrap.ps1` 串行 10 步幂等；`demo.py` 10 问覆盖 6 路由。
- 评估闭环：召回消融 / 意图混淆矩阵 / RAGAS / 四档压测，未达标项均有根因分析与改法记录（这在同类项目中非常罕见）。
- 扣分点：部分指标未达标（Recall@5 0.7071 < 0.85、faithfulness 0.7075 < 0.85、QPS 2.686 < 3）属于功能质量而非维护性问题；前端缺单测；无监控指标。

## 二、代码层面问题与优化建议

> 优先级定义：P0=线上已造成事故或高危；P1=明确缺陷/成本风险，建议 1 周内处理；P2=质量改进，1 个月内处理。

### P1-1 匿名限流在反向代理后失效（线上适配缺口，关键）

**问题**：`app/core/ratelimit.py` 的 `_client_ip()` 取 `request.client.host`（TCP 对端），明确不信任 XFF——这是"本机直连部署"的假设。但线上是 nginx 反代（`deploy/nginx-lawanswer.conf` 的 `/api/` location），所有匿名请求的 peer 都是 `127.0.0.1`。

**后果**：匿名 20 次/分钟的限额退化为**全站共享一个桶**——所有未登录用户合起来每分钟只能问 20 次，且任何单用户刷满会影响全部匿名用户；同时限流完全失去了按 IP 区分的能力。

**建议**：给配置加可信代理开关，如 `TRUST_PROXY=true` 时取 `X-Real-IP`（nginx 已设置）或 XFF 最后一跳；默认保持现状。同时把"直连 vs 反代"写进部署文档注意事项（部署文档第 2.1 节只提了安全组，没提限流语义变化）。

### P1-2 登录失败锁定只有"按用户名"维度

**问题**：`_check_locked` / `_record_failure` 的 key 是 `login:fail:{username}`。

**后果**：① 攻击者跨用户名轮询爆破无节流（每个用户名 5 次/60s 独立计数）；② 任何人都能对指定用户名刷 5 次失败，锁死对方 60s（轻量 DoS）。

**建议**：叠加 `login:fail:ip:{ip}` 维度（如 20 次/分钟/IP 全局限流），用户名维度保留。生产环境可把锁定窗口调大（当前 60s 偏短）。

### P1-3 验证码的故障语义不对称：生成 fail-closed、校验 fail-open

**问题**：`captcha.py` 在 Redis 不可用时：`new_captcha` 抛 `UpstreamError`（502，无法出题）；`verify_captcha` 却降级放行（返回 True，只记 warning）。代码注释也写明"生产部署时应把该降级关掉"——但没有配置开关。

**后果**：线上 Redis 故障时，登录页完全打不开（本次 P0 事故的直接触发环节）；而一旦 Redis 恢复前有人能绕过出题（例如直连 API），校验又全部放行，验证码形同虚设。

**建议**：
1. 加配置项 `CAPTCHA_FAIL_OPEN=false`（prod 必须 false），校验侧不再放行；
2. 出题失败时前端收到 502，应自动重试 + 显示"稍后自动重试"倒计时，而不是停在"加载中…"（见线上 P1-2）。

### P1-4 上传解析并发无上限

**问题**：`upload_documents` 用 FastAPI `BackgroundTasks` 直接 `add_task(run_ingest_job)`，每个任务阻塞一个线程跑完整入库（CPU 向量化，单文件数十秒到分钟级），且无并发上限。

**后果**：连续上传 N 个文件 → N 个并行 CPU 向量化任务 → 2 核小机器 CPU 打满、内存叠加，可能拖垮问答链路。

**建议**：用信号量（如 `max_active_ingest=2`）或独立队列（如 arq/RQ）限并发；任务失败已在 `run_ingest_job` 内落库 failed，只需加并发闸门。

### P1-5 前端全量引入 Element Plus，打包体积大

**问题**：`frontend/src/main.ts` 直接 `app.use(ElementPlus)` 全量注册（含全部组件与样式）。`npm run build` 产物里 vendor 包体量大（线上 `element-plus-D7cQ737J.js` 单独一个 chunk）。

**建议**：改用 `unplugin-vue-components` + `unplugin-auto-import` 按需引入（Element Plus 官方推荐），vendor 体积可再减约一半；对首屏加载（尤其 2 核小机器 + 移动端）收益明显。

### P1-6 前端 `retry()` 绕过 Pinia 直接改 store 状态

**问题**：`ChatView.vue` 的 `retry()` 里 `chat.messages.pop()` 直接改 store 的响应式数组，绕过 store action；与 store 内其他操作（如 `removeSession` 的乐观回滚）风格不一致，后续若加持久化/归一化容易漏。

**建议**：在 chat store 增加 `retryLast()` action，视图只调 action。

### P2-1 `RequestIDMiddleware` 用 `BaseHTTPMiddleware`

**问题**：`BaseHTTPMiddleware` 对每个请求有额外调度开销，且历史上对流式响应（SSE）有缓冲/生命周期兼容问题；本项目 SSE 是核心链路。

**建议**：改为纯 ASGI 中间件（`app.add_middleware` 换成手写 ASGI wrapper），保留 request_id 注入与访问日志，减少每帧开销。

### P2-2 缺监控与告警

**问题**：只有 `/api/health`（依赖探活）和日志，无指标端点、无结构化错误追踪、无告警。本次 Redis 故障若无人工访问健康检查，不会有人发现。

**建议**：加 `/metrics`（prometheus-client 简单暴露：请求数/延迟/LLM 调用数/429 次数/Redis-MySQL-Milvus 状态），配 Node 级磁盘/内存告警；至少给 systemd 服务加 `Restart=on-failure` 已在，补磁盘水位 cron 检查。

### P2-3 前端无自动化单元测试

**问题**：前端只有 `e2e/walkthrough.mjs`（走查脚本）和后端 contract test，无 vitest 单测；SSE 事件归并、表单校验、会话乐观更新等逻辑全靠人工验证。

**建议**：用 Vitest 给 chat store（SSE 归并、切换会话竞态、追问校验）、表单校验、`useSSE` 补关键单测，`npm run test` 进 CI。

### P2-4 模型内存占用与成本（架构层）

**问题**：bge-m3 + bge-reranker 进程内加载约 4.6G 常驻（CPU 无 fp16），部署方案已明确"2G 机器跑不动、8G 刚好够"。线上当前能跑通说明已升配，但内存预算仍然很紧（Milvus 2.5G + MySQL + 模型 4.6G）。

**建议**（三选一）：① 维持自托管，确保实例 ≥8G 内存；② 换 DashScope `text-embedding-v3` API 化 embedding（1024 维对齐，省 2.3G，`app/ingest/embedder.py` 已留 Protocol 接口）；③ reranker 加配置开关 `RERANK_ENABLED`（当前 `use_rerank` 只是函数参数，无环境变量），小规模演示可关。

### P2-5 其它小项

- `qa_cache._on_hit` 每次新命中都写一次 MySQL `hit_count`（热路径写库），命中量大时可批量/异步化；低危。
- Swagger `/docs` 公网可见，暴露全部 API 结构；生产建议 `DEBUG=false` 时关闭 docs 或加 Basic Auth。
- `production.env.example` 中 Redis 密码留空且 docker-compose 未加 `--requirepass`；若安全组被误放行 6380，等于未授权 Redis。至少把"安全组只放 443/22"写成部署检查清单项。
- `.env`（本地）含 JWT_SECRET 与数据库密码，`assert_secrets_not_in_dotenv` 只拦 LLM 密钥；建议对 `JWT_SECRET` 也做 prod 强制（生产已强制，本地无所谓）。

## 三、线上运行层面实测结果与问题

### 3.1 实测基线（正常的部分）

| 项 | 结果 |
|---|---|
| HTTPS/证书 | 正常（有效证书，443 可达） |
| 核心问答链路 | **正常**：匿名 SSE 实测 3.4s 完成"意图→检索→重排→4 条来源→流式生成"，回答带正确法条引用（劳动合同法第 19/83/70 条 + 高频问答第 20 条），质量好 |
| LLM 密钥 | 已配置（`llm_key_configured=true`，来源 `LLM_API_KEY`，模型 `deepseek-v4.1-flash`） |
| Milvus | ok（51ms，collection `law_chunks` 存在） |
| MySQL | ok（96ms） |
| 端口暴露面 | 良好：6380/3307/19531/9002/9003/8101/9092 外部均不可达，仅 443/22 开放 |
| 静态资源缓存 | index.html `no-cache` + 哈希资源长缓存（线上实际为 `no-store, no-cache, must-revalidate`，更保守，可接受） |

### 3.2 P0-1 【正在发生】Redis 磁盘持久化失败 → 验证码 502 → 全站无法登录/注册

**证据**：`/api/health` 返回 `services.redis.status=down`，错误为
`ResponseError: MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk...`；
浏览器实测登录页与注册页均提示"验证码服务暂不可用，请稍后重试"，`/api/auth/captcha` 502，控制台 3 次 502。

**因果链**：Redis `appendonly yes`（docker-compose 配置）写 AOF 到 `./volumes/redis`，持久化失败典型根因是**宿主磁盘满**或该目录权限/挂载问题 → Redis 进入只读保护（MISCONF）→ 验证码写入失败 → 出题 502 → 前端登录/注册全挂。而前端路由守卫强制登录（见 P1-5），所以**产品当前对用户整体不可用**（只有绕过前端直连 API 才能匿名问答）。

**立即处置**（按序）：
1. 登录服务器执行 `df -h /`、`du -sh /opt/lawanswer/volumes/redis /var/lib/docker/*` 定位满盘；
2. 清理：`docker system prune`、日志上限（部署方案已建议容器日志 20M，确认生效）、删除旧镜像；
3. 若 `volumes/redis` 所在分区确实写不下，迁移 Redis 数据目录或扩容磁盘；
4. 确认后 `docker compose restart redis`，`/api/health` 变绿，验证码即可恢复；
5. 兜底：若磁盘短时间无法扩容，先把 redis 的 `appendonly no`（纯内存 + 定期 RDB）降风险，数据可重建（缓存/验证码/登录计数均为可丢数据）。

### 3.3 P1-1 线上 nginx 未下发安全响应头

**证据**：`/chat`、`/index.html`、`/api/health/live` 的响应头中 `X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy` 全部为空；而仓库 `deploy/nginx-lawanswer.conf` 明明写了 `add_header ... always` 三行。

**结论**：线上部署的 nginx 配置与仓库不一致（可能手改过、或部署时用了另一份 conf）。顺带缺 `Strict-Transport-Security`（HSTS）。

**建议**：以仓库 conf 为基准核对线上 `/etc/nginx/conf.d/lawanswer.conf`，补齐三行安全头，并追加 `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`（确认证书续期链路 OK 后再开）。

### 3.4 P1-2 前端验证码失败无自动重试与降级提示

**证据**：验证码按钮从"加载中…"直接变成"验证码服务暂不可用"，刷新按钮点击后仍失败，页面无自动重试、无倒计时。

**建议**：`CaptchaField.vue` 对 `502/upstream_error` 做指数退避自动重试（如 3 次，间隔 2s/5s/10s），并在按钮上显示"稍后自动重试 (Ns)"；后端恢复后用户无需刷新页面。

### 3.5 P1-3 前端部署非原子，存在"新 index.html + 旧资源 404"窗口

**证据**：实测过程中 index.html 一度引用 `index-Be2LGv.js`（旧哈希）→ 404，随后页面已切换到 `index-BeBy2LGv.js`（新哈希）正常。说明发布是覆盖式上传 dist，切换瞬间会有一批用户拿到新旧混搭。

**建议**：改为原子发布：`release.sh` 把新 dist 解压到 `dist-<版本号>`，nginx root 软链 `current → dist-<版本>`，`ln -snf` 原子切换后删旧目录；或至少"先传 assets、后传 index.html"的顺序发布。

### 3.6 P1-4 前端强制登录才可进入 /chat

**证据**：访问 `/chat` 被路由守卫重定向到 `/login?redirect=/chat`；后端 `get_current_user_optional` 本就支持匿名问答。

**建议**：对演示/引流站点，建议匿名可聊（匿名 20 次/分限流已足够防护，修复 P1-1 后按 IP 生效），登录仅用于会话持久化/知识库管理；降低首次使用门槛。若坚持必须登录，则 P0-1 的后果更严重（登录全挂 = 全站不可用）。

### 3.7 P2-1 SSH 22 全网开放

**证据**：端口探测 `22 OPEN`；部署方案明确要求安全组 22 仅放行"你的本地公网 IP/32"。

**建议**：控制台把 22 收紧为你的出口 IP（或 0.0.0.0/0 换密钥登录 + `PasswordAuthentication no`）；本次 Redis 处置会用到 SSH，顺手处理。

### 3.8 P2-2 延迟基线与小规格实例压力

**证据**：MySQL 健康延迟 96ms、Milvus 51ms（本机直连应 <10ms 量级）；2 核实例 + 4.6G 模型常驻，内存/CPU 余量小。Redis MISCONF 也可能与磁盘/IO 饱和相关。

**建议**：处置 P0-1 时一并看 `free -m`、`vmstat`、`uptime`；若常驻内存逼近上限，按 P2-4 减负（关 reranker 或 API embedding）。健康检查加"磁盘水位"探针（`df` 使用率 >85% 告警），避免下次再无声炸掉 Redis。

## 五、验证方式与局限

- **代码层**：通读 app/ 全部 30 余个模块与前端 src/；本机 `pytest` 675 passed / 49 skipped；未读的文件：`app/eval/` 六个评估脚本细节、`app/ingest/{clean,chunker,structure,normalize,loaders,writer}.py` 的部分实现（有测试覆盖）、前端 4 个视图细节样式。评估以主干链路 + 测试 + 架构为准。
- **线上层**：浏览器实测登录/注册页、健康检查、匿名 SSE 问答、响应头、端口暴露面；未做登录后会话/知识库管理页实测（登录被验证码阻断，属事故本身的一部分）；未做并发压测（避免给线上制造压力）。
- **局限**：无法从外部确认 Redis MISCONF 的最终根因是磁盘满还是权限问题（需 SSH 上机确认）；`/docs`、nginx 具体 conf 内容、实例规格等无法从外部核实，建议按报告指引上机核对。
