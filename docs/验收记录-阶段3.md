## 三、延迟问题（必须暴露的问题）

| 环节 | CPU 耗时 | 说明 |
|---|---|---|
| query 编码（bge-m3） | ~0.2–0.3s | 单条文本，可接受 |
| Milvus 双路检索 + RRF | ~0.1s | 1470 条规模，几乎无感 |
| **重排（20 条 × 200 字）** | **~6.5s** | 瓶颈 |
| 首次请求额外开销 | +40s | 模型加载（bge-m3 40s + reranker 45s，进程级单例，只付一次） |

**已做的优化**：正文裁剪到 200 字、`max_length` 512→256、批大小 16、模型进程级单例（原来每次请求都会重新加载，属于致命 bug，已修）。耗时从 9.4–11s 压到 6.7–7.4s。

**根因**：PyPI 的 torch 是 CPU 构建（`torch.cuda.is_available()=False`，`2.14.1+cpu`）。
**解法**：装 CUDA 版 torch 后把 `EMBEDDING_DEVICE` 改为 `cuda`，20 条重排预计 150–250ms，整体可进 0.5s 内。

尝试过安装 `torch==2.9.1+cu126`，代理带宽下 21 分钟仍未下载完（约 2.5GB），已中止以免破坏环境；命令已写进 README「GPU 加速（可选）」，随时可重试。

## 四、实现要点

```
question
  → bge-m3 编码（dense 1024 + sparse）
  → Milvus hybrid_search：dense(HNSW/COSINE, ef=64) + sparse(SPARSE_INVERTED/IP, drop=0.2)
  → RRFRanker(k=60) 融合
  → bge-reranker-v2-m3 重排（正文裁剪 200 字，max_length 256）
  → 按 parent_id 去重（同条多子块留最高分）
  → 截断 topK
  → MySQL 批量回表取整条法条（IN 一次查询）
```

* **进程级单例**：`get_embedder()` / `get_reranker()` 原本每次 new 一个实例，导致每个请求重载 2GB 权重。这是本次修掉的最严重的性能 bug。
* **空稀疏向量降级**：极短 query（如单个字）产不出稀疏词项时自动退化为纯稠密，避免 Milvus 报错。
* **父块回表失败可降级**：MySQL 异常时用子块正文继续，不让整次检索失败。
* **消融开关**：`mode=dense|hybrid` × `use_rerank=true|false` 四个组合可直接跑，阶段 7 的 L1–L3 组复用同一套代码。

## 五、消融现状（提前说明，不作为阶段 3 结论）

8 条样本下：**仅稠密 Recall@5 = 1.000，混合+重排 = 1.000**，没有区分度。
原因是样本太"标准"（问题与条文用词高度重合），且语料只有 1470 块。
→ 阶段 7 必须用更难的样本（口语化、多跳、跨条推理）才能体现重排价值，这一点已记入评估计划。
