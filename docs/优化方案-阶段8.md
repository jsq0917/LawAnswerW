## 四、P1 — 性能优化（第二周）

### P1-1 缓存前置：高频问题跳过意图识别

**现状链路**：
```
用户提问 → 意图识别 LLM（~1.0s）→ 路由 → qa_cache 精确命中？→ 命中则纯结构化回放
```

高频问题已经在 Redis 里有精确答案，却白白花 1s 调 LLM 做意图识别。

**改法**：把 `app/orchestration/service.py` 的 `analyze_query` 改成两段式：

```
用户提问
  ↓
先算 normalize_question → 查 Redis qa:exact:{sha1}
  ↓ 命中？
  ├─ 是 → 直接构造 pure_structured 的 QueryPlan，跳过 LLM 意图识别
  └─ 否 → 走原流程：LLM 意图识别 → 路由 → qa_cache 再查一次（BM25+余弦门）
```

**关键点**：
- Redis 精确命中是 0.1ms 级的，先查它几乎零成本
- 命中后不需要 intent_result，但 QueryPlan 需要一个——构造一个"伪 IntentResult"（intent=labor_law、route=pure_structured、source="cache"）即可
- 未命中时原流程不变，第二次查 qa_cache 是 BM25+余弦（不是精确缓存），不冲突

**预期收益**：
- 高频问题 TTFT：2.1s → 0.1s（回放打字机效果，首帧 1-3ms）
- QPS：高频问题占比假设 30%，整体 QPS 提升约 30-40%

**验证**：
- 发一个已知高频问题（如"试用期最长可以约定多久"），看日志里是否有"意图识别(LLM)"这行——应该没有
- 看 SSE meta 的 `degraded` 字段或新增一个 `cache_hit=true` 标记
- 压测重跑 `loadtest.py --levels 1 5 10 20`

### P1-2 _cosine 改用 numpy

**现状**：`qa_cache.py` L360-364 纯 Python 循环算 1024 维向量点积，每次 1024 次 Python 乘法。

**改法**：
```python
# 现在
denom = (sum(x*x for x in a)**0.5) * (sum(y*y for y in b)**0.5)
return sum(x*y for x,y in zip(a,b)) / denom

# 改成（embedder 返回的 dense 本来就是 list[float]，转 numpy）
import numpy as np
a = np.asarray(a, dtype=np.float32)
b = np.asarray(b, dtype=np.float32)
return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))
```

**预期收益**：每次 qa 门检查从 ~5ms 降到 <0.5ms。

**验证**：现有 `test_qa_cache.py` 全绿即可，不需要新测试。

### P1-3 意图识别与生成并行（可选，难度高）

**现状**：意图识别 ~1.0s 是串行的，必须等它返回才能开始检索和生成。

**改法**（如果 P1-1 做完 QPS 还不够 3）：
- 意图识别和"初步检索"并行：先用原 query 直接做一次 Milvus 检索（不做 law_hints 过滤），同时等意图识别结果
- 意图返回后，如果 law_hints 与初步检索的范围不一致，再补一次过滤后的检索
- 这是工程优化，不影响质量

**注意**：这会让代码复杂度上升，P1-1 做完如果 QPS 已经过 3 就不做。

## 五、P1 — 质量优化（第三周）

### P1-4 多跳检索：子查询独立取 topK + 全局重排

**现状**：`stream.py._retrieve()` 遍历 `plan.sub_queries`，每个子查询都用完整 topK=8，合并去重后直接用。

问题：
1. 3 个子查询 × topK=8 = 24 个候选，去重后可能只有 10-12 条，但没有全局按 rerank_score 重新截断到 8
2. 每个子查询都做完整的重排（reranker），重复计算
3. 评估脚本 `recall_eval.py` 根本没走 sub_queries，数字不反映真实链路

**改法**：

1. **生产链路 `stream.py._retrieve`**：
   - 每个子查询只取 pool（候选池），不做最终截断
   - 所有子查询的候选合并后，**统一做一次 rerank**（而不是每个子查询各做一次）
   - 按 rerank_score 全局排序，截断到 `topk_for(complexity)`
   - 这样：子查询 1 的第 3 名和子查询 2 的第 5 名会在同一个池子里公平排序

2. **评估脚本 `recall_eval.py`**：
   - 改成走完整 `analyze_query(query)`，拿到 `sub_queries` 后按上面的逻辑检索
   - 这样 Recall@5 的数字才反映真实生产链路
   - 预期数字会比现在的"单查询直检"高（因为 decompose 的子查询确实召回了更多条）

**预期收益**：
- 多跳 Recall@5：0.48 → 0.70+
- 评估数字与生产一致，不再"评测是一套、线上是一套"

**验证**：
- `uv run python -m app.eval.recall_eval` 重跑，看 multi_hop 和 complex 两类的 Recall@5
- 人工抽 5 条多跳问题，看 sources 里是否覆盖了期望的全部法条

### P1-5 Prompt 收紧：引用格式硬约束 + 计算类不给数字

**现状**：
- Prompt 说"每个结论后标注依据"，但模型经常漏写条号（REPORT §6.2 案例 #2/#4）
- Prompt 要求"代入示例"，但语料没有具体工资数字，示例数字是编的（拉低 faithfulness）

**改法**（改 `app/generation/prompts.py` 的 SYSTEM_PROMPT）：

1. **引用格式加硬约束**：
   ```
   【引用格式】（加强版）
   - 只要陈述了某条法律的具体规定（包括"应当/不得/可以/视为"等法条措辞），
     必须在该句末尾用（《法名》第X条）标注。
   - 标注不全视为不合格：如果一个结论引用了多条法律依据，必须逐条标注，
     不能只写其中一条。
   - 引用中的法律名与条号必须与【参考资料】完全一致。
   ```

2. **计算类问题改法**：
   ```
   【计算类问题】（收紧版）
   涉及经济补偿、加班费、赔偿金等计算时，给出计算公式和变量说明：
   - 公式格式：经济补偿 = N × 月工资基数
   - 变量说明：N = 工作年限（每满一年算一个月，不满六个月算半个月），
     月工资基数 = 离职前 12 个月平均工资
   - 不要编造具体数字示例（如"你能拿 5 万元"），因为资料里没有用户的工资数据。
   - 资料未覆盖的计算规则，明确说"现有资料未涉及具体计算基数"。
   ```

3. **免责句固定尾注**：
   把"具体以裁判机关认定为准"从正文断言里移出来，改成固定尾注，不计入正文：
   ```
   【尾注】（每次回答自动追加，不算正文）
   以上分析仅供参考，具体以裁判机关认定为准。
   ```

**预期收益**：
- 引用命中率：80% → 95%+
- RAGAS faithfulness：0.71 → 0.80+

**验证**：
- `uv run python -m app.eval.ragas_eval --collect && uv run python -m app.eval.ragas_eval` 重跑
- 人工抽 10 条，数一下"写了结论但没标条号"的次数

### P1-6 评估样本扩充到 120 条

**现状**：40 条样本，每类意图只有 4 条，acc=1.00 的统计意义很弱（换 1 条就变 0.95）。

**改法**：
1. 在 `eval/qa_test_cases.jsonl` 里补到 120 条
2. 每类意图（labor_law / civil_code / general / greeting / other）至少 15 条
3. multi_hop 和 complex 两类从 8/8 条扩到各 20 条
4. 每条样本必须标注：期望法条（法名#条号）、题型（single_hop/multi_hop/complex/no_answer）、语料是否覆盖
5. 新增"漏引条号"检查：答案里提到的法条内容是否都标了条号

**预期收益**：评估结果统计显著，换一条样本不会让指标跳 5 个点。
