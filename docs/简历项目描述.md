## 一句话版本（项目列表用）

> **LawAnswer**：面向中国法律条文的多路 RAG 问答系统。以"条"为不可切割边界做父子分块，bge-m3 稠密+稀疏双路

## STAR ① 检索链路：从"能召回"到"召回得准"（投后端 / 算法工程岗）

**Situation**
法律问答的检索有两个硬约束：法条不能被切断（截断一条就答错），且用户问的是生活语言（"哺乳期能不能安排加班"）
而语料写的是法言法语。直接用通用 RAG 的固定窗口分块 + 稠密检索，法条会被切碎，术语也对不上。

**Task**
负责解析与检索两层：把三部法律（劳动合同法 98 条 / 劳动法 107 条 / 民法典 1260 条）结构化入库，
并在 2k 块规模下把 Recall@5、MRR 做到可用。

**Action**
1. **用真实语料分布反推参数，而不是拍脑袋**：统计出条文均值 97 字、中位 76 字、P90 186 字，
   于是把子块定为 300/50 —— 若沿用 500 窗口，父子分块会退化成 1:1，等于白做。
2. **以"第X条"为硬边界**做父块、条内款项做子块；检索命中子块后回填父块，保证生成端看到的永远是完整法条。
3. **脏数据治理**：劳动法 PDF 含 1,122 个康熙部首变体字符（"第⼀条"），不做归一化只能识别 6/107 条，
   写了 7 类清洗规则 + 字符归一，把条数做成入库硬断言（98/107/1260，不符直接 failed）。
4. **检索分四组做消融**（纯稠密 / 混合 / +重排 / +法域过滤），用 40 条人工标注样本量化每一刀的收益；
   再加一组固定窗口对照组，先把评测口径本身校准正确（首版按条截断导致召回虚低到 0.23，改为按窗口并集后 0.7571）。

**Result**
- 法条截断率 **0.00%**（目标 ≤3%），三部法律条数校验 **98 / 107 / 1260 全对**，劳动法条号识别率 **6/107 → 107/107**。
- 单跳问题 Recall **15/15 = 1.000**；整体 Recall@5 **0.7071**、MRR **0.6886**。
- 消融给出两个反直觉结论并据此决策：加权 RRF（0.75/0.25）**无收益已证伪回退**；
  按意图 `law_hints` 做法域预过滤反而把 MRR 拉高 **+4.6pt**、Recall@1 **+8.6pt**。

**面试追问准备**
- Q：Recall@5 只有 0.71，是不是方案不行？
  A：单跳 100%，缺口全在多跳（~0.48）。根因是多跳问题仍走单查询直检，没启用 decompose 多子查询检索 —— 这是已知且已定位的下一步，不是没发现。
- Q：为什么混合检索不如纯稠密？
  A：先假设是"等权 RRF 让稀疏路稀释了稠密序"，改成稠密主导的加权 RRF 后召回**没有回升**，假设被证伪；
  复核后归因是稀疏路挤占了候选池名额（同样 20 个名额两路各取一半，正确条连候选都进不了）。
  业务上若要单跳最优可切 `RETRIEVAL_MODE=dense`（Recall@5 高 3.8pt、MRR 高 4.4pt），但会丢术语精确匹配，是取舍不是 bug。

## STAR ② 质量闭环：用评估驱动 Prompt 改进（投 AI 应用 / 算法岗）

**Situation**
初版上线后 RAGAS faithfulness 只有 **0.5189**，距离 0.85 差 33 个百分点。但"忠实度低"是个模糊结论，
不知道该改检索、改 Prompt 还是改模型，凭感觉调参只会来回震荡。

**Task**
搭一套可复现的评估闭环，把"感觉不好"变成"哪一项差、差多少、改了之后动了多少"。

**Action**
1. **造样本**：按单跳 15 / 多跳 12 / 复杂 8 / 无答案 5 分层做 40 条 QA，每条标注期望法条并
   **程序化校验该法条是否真实存在于语料**（第一轮就揪出 5 条参考答含语料外内容，已改写）。
2. **四件套脚本**：`recall_eval`（5 组消融 + 分题型拆解 + 延迟）、`intent_eval`（20 条，acc/macro-F1/混淆矩阵，
   带规则兜底基线）、`ragas_eval`（先采集回答再打分，可续跑）、`loadtest`（asyncio SSE 四档并发）。
3. **定位而非猜测**：把 faithfulness 低归因到具体段落 —— Prompt 的"实务提示"段允许模型自由发挥且无出处。
4. **定向改 Prompt 并复测**：要求实务提示必须基于参考资料且标注条号、资料未涉及直接省略，
   回答结构改为"先结论 → 再依据 → 最后实务提示"。

**Result**
- faithfulness **0.5189 → 0.7075（+18.9pt）**，这是整个项目单点收益最大的一次改动。
- **无答案组 5/5 不编造**（这是法律场景的底线，也是专门设 5 条 no_answer 样本的原因）。
- 意图识别 **acc / macro-F1 = 1.0000 / 1.0000**（20 条样本；纯规则基线仅 0.60，证明 LLM 那一跳有价值）。
- 副作用也被量化并记录：answer_relevancy **−9.3pt**（答案更"纯法条"），属于知情取舍而非意外。

**面试追问准备**
- Q：剩下 14pt 差距在哪？
  A：定位到两处 —— 计算示例里模型自己代入的数字、"以裁判机关认定为准"这类免责句。下一步是计算类只给公式不给数字、免责句改固定尾注。
- Q：为什么不直接换更强的模型？
  A：换模型是把问题藏起来。先量化再定向改，才能知道每一刀值多少；而且 0.52→0.71 靠的是 Prompt 约束，成本为零。

## STAR ③ 性能与稳定性：把瓶颈从 40 倍追到 1.1 倍（投基础架构 / 高性能方向）

**Situation**
首轮压测 QPS 只有 **0.173**（并发 1），目标 ≥3，差 17 倍；TTFT p50 6.59s，用户根本等不下去。
如果只报"模型太慢"，那这个结论既不能指导优化，也经不起追问。

**Task**
定位真实瓶颈并把性能追到可接受区间，同时保证高并发下不出错。

**Action**
1. **先做归因，不急着优化**：拆出"编码 / 检索 / 重排 / LLM"四段耗时，发现 CPU 下单条 query 编码 ~250ms、
   20 条重排要 5–14s —— 瓶颈根本不在 LLM，在embedding 与 reranker。
2. **落地 GPU**：本机确认有 RTX 4060 Laptop（驱动 CUDA 13.3），此前"无 GPU"是装了 CPU 版 torch 的误判；
   装 `torch 2.14.1+cu130`（cu128 无 cp313 Windows 包，最终走本地 wheel 安装），两模型启用 fp16。
3. **工程化防退化**：踩到 `uv sync` 会把手工装的 GPU 版 torch 换回 CPU 版的坑，
   固化成 `uv sync --no-install-package torch` + `uv run --no-sync`，并写进一键脚本自动判定。
4. **压测按 SSE 帧计 TTFT**（不是按响应结束计），四档并发 × 30 次，每档先清缓存并预热，用随机后缀绕开精确缓存。

**Result**
- 单条 query 编码 **250ms → 28ms（8.9×）**；20 条重排 **5–14s → 137ms（36–100×）**，满足 ≤200ms 目标。
- QPS @ 并发 10 **0.289 → 1.994（6.9×）**，@ 并发 20 **0.303 → 2.686（8.9×）**；TTFT p50 **6.59s → 2.12s（3.1×）**。
- **错误率 0.00%（两轮 240/240 全成功）**，无超时、无 5xx、无 SSE 协议异常。
- 瓶颈已完成转移：现在 2.1s TTFT 里检索只剩 ~0.7s，**大头变成两次 LLM 调用**（意图 ~1.0s + 生成首 token ~0.4s）。

**面试追问准备**
- Q：为什么没到 3 QPS？
  A：并发 20 时显存吃满开始排队，且每条请求固定两次 LLM 调用受上游并发上限约束。想破 3 要么对高频问题前置问答缓存跳过意图识别，要么把意图与生成合并成一次调用。
- Q：GPU 之后还剩什么？
  A：从"差 5–40 倍"追到"差 1.1–1.8 倍"，剩下的是架构问题（两次串行 LLM 调用）而不是资源问题。
