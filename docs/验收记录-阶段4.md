## 六、真实 LLM 意图评估（2026-10-23 补跑，已达标）

```powershell
uv run python -m app.eval.intent_eval              # LLM 路径，产出 eval/results/intent.json
uv run python -m app.eval.intent_eval --rules-only # 同批样本的规则基线，对照用
```

样本 `eval/datasets/intent_samples.json`（5 类 × 4 条 = 20 条，人工标注），结果 `eval/results/intent.json`。

| 指标 | 目标 | 实测 |
|---|---|---|
| accuracy | ≥0.90 | **1.0000**（20/20） |
| macro-F1 | ≥0.88 | **1.0000** |
| 延迟 p50 / p95 / max | — | **970 / 1291 / 1563 ms** |
| 来源 | LLM 优先、失败兜底 | llm **20** / rules 0 |
| 改写类型分布 | — | direct 15、decompose 5（多问句与跨法对比自动拆 2 条子查询） |

逐类 P/R/F1（support 各 4）：labor_law、civil_code、general、greeting、other **均为 1.000**。

首跑（同批样本、同一把 key）只有 **0.8500 / 0.8425**，未达标。三个原因都不是"模型不行"：

1. **意图客户端漏下发 `thinking=disabled`（实现缺陷，主因）**
   `get_intent_client()` 没把 `settings.llm_thinking` 传给 `LLMClient`，而 DeepSeek 思考模式**默认 enabled**：
   隐藏推理计入 completion_tokens（同一 prompt 两次 347 / 510 tokens），延迟由 ~1.0s 涨到 2–10s，
   3s 超时下必然偶发降级——样本 G02 两次分别耗时 6.8s / 10.8s 后走规则兜底，判成 labor_law。
   修复后同一查询稳定 ~1s，20 条无一降级。回归用例：`tests/test_intent_llm.py::TestIntentClient`。
2. **Prompt 对"能力询问"缺一条规则**："你能做什么"被判成 greeting（规则侧本来能判对 other），已补明
   "你能做什么/有哪些功能/你是谁 → other"。
3. **`INTENT_TIMEOUT_S` 3s 偏紧**：修好 thinking 后 p95≈1.1s，仍上调至 **5s** 留抖动余量——超时即降级规则兜底，
   而规则基线只有 0.60，宁可多等 1s 也不掉准确率。

另修正 1 条标注歧义样本：原 G03"打劳动官司一般要走哪些流程"按"泛法律→general"标注但领域归属可争议，
已换成"打民事官司和行政诉讼在流程上有什么区别"（跨民诉/行诉，明确属 general）。

**局限**：这 20 条是**开发集**（首跑未达标后做过 3 处修复 + 1 处标注澄清），1.0000 不代表线上分布；
阶段 7 用 40 条 QA 做全链路复测，必要时另建一批未见样本做留出验证。
