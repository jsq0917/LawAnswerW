## 三、跑通过程中修掉的问题

| # | 问题 | 定位与修复 |
|---|---|---|
| 1 | `uv sync --group eval` 报 "Could not find a suitable Python executable" | uv 缓存的解释器路径指向已被删除的 `.workbuddy/binaries/.../3.13.12`；用 `--python` 显式指向 `%APPDATA%/uv/python/cpython-3.13.12...` 装上 |
| 2 | ragas 0.3.0 没有 `context_relevance` 小写导出，也没有 `wanted` 变量 | 该指标只有 `ContextRelevance` 类名；结果列名是 `nv_context_relevance`，改为「逻辑名 → 实际列名」映射 |
| 3 | 参考答写了语料外内容（年假 5/10/15 天、司法解释三个月规则等）导致 context_recall 系统性低估 | 5 条参考答改为只写语料能支撑的表述；并把修正同步进 `qa_answers.jsonl`（RAGAS 读的是这份，不是样本文件） |
| 4 | 固定窗口 D 组第一版召回 0.231，明显失真 | 口径错：把每个窗口拆成多条法条后再按"条"截断 top-k，等于只算前 2 个窗口；改为**按窗口**计（top-k 窗口覆盖的条号并集），得 0.7571@5 |

## 六、已知遗留

1. **召回偏低**：加权 RRF / 法域预过滤 / 重排候选池扩容均未实施（改法已写在 REPORT §4.2）。
2. **召回评测走单查询直检**，没接 `analyze_query` 的 decompose 多子查询编排，多跳题分数被低估（方法学偏差）。
3. **RAGAS judge 与生成同模型**（都是 `deepseek-flash`），存在自我偏好/严厉度偏差；未换 judge 复核。
4. **D 组未做人工核对**：固定窗口跨条拼接可能导致混引，本轮只量化了召回，没验生成质量。
5. **TTFT/QPS 受 CPU 限制**，与阶段 3 是同一根因（`torch 2.14.1+cpu`），装 CUDA 版 torch 后可重测。
6. 40 条样本是**开发集**（写题时就参照了语料），线上分布的代表性未验证。
